# SmartDoc 商业化 P0 可靠性与安全设计

## 1. 目标

在现有 SmartDoc 微服务基础上完成商业化前的 P0 应用与运维加固：定义可量化的可靠性目标，守住认证和租户隔离边界，保证异步任务可恢复，限制依赖故障扩散，补足运行指标与备份恢复验证。改造保持本地 Docker Compose 一键部署可用，并为通用自托管、单地域多节点部署提供明确边界。

本阶段不宣称单机 Compose 已达到商业高可用。跨主机副本、MySQL/Redis/RabbitMQ/MinIO 集群和实际故障切换演练属于后续基础设施阶段；本阶段提供应用层保护、可复现测试和所需运维要求。

## 2. 当前状态与既有能力

- 网关已配置按用户维度的 Redis 令牌桶限流，AI 请求与普通请求使用不同额度。
- 多个服务已暴露 Actuator health、info、Prometheus 指标端点。
- 生产 Compose 只发布 Nginx 的 80/443；微服务和中间件使用容器内部网络。
- 已有 JWT/内部服务密钥、跨租户测试、数据库备份和恢复演练脚本。
- Toolbox 任务以 MySQL 状态为主，可从待处理任务恢复；AI 异步任务当前将状态保存在 Redis 后再发布 RabbitMQ 消息，仍存在状态和消息无法原子提交的窗口。
- 代码已使用服务内 `@Transactional`，未实现跨服务事务；没有统一的熔断与并发隔离策略。

实施必须复用现有能力，先补缺口，不另建平行鉴权或限流体系。

## 3. 范围

### 3.1 可靠性目标和边界

新增运维说明，为登录、文档读写、文件上传、RAG 检索和 AI 生成分别定义 SLI/SLO、统计窗口、错误预算、RPO 和 RTO 的填写与验收方法。文档必须区分应用接口延迟与外部模型等待时间，不把尚未在目标部署环境测得的值写成承诺。

### 3.2 安全与租户回归

- 扩展现有自动化测试，验证伪造用户/角色/企业/内部服务头不能越权，企业 A 不能读取企业 B 的文档、任务或检索片段。
- 限流依赖不可用时采用明确的失败关闭策略；限流不能绕过身份认证，未认证请求使用受限的来源地址维度。
- 检查业务日志，禁止记录 Token、密钥、完整用户问题、文档正文和完整提示词；用 traceId、任务 ID、用户 ID、长度和错误类别保留可诊断性。
- 保留现有文件扫描和输入限制；不得为提高可用率而在扫描服务不可用时放行文件。

### 3.3 异步任务一致性和恢复

- Toolbox 的 MySQL 任务状态与定时恢复机制继续作为既有持久化基础，增加对消息重复投递、发布失败、消费者崩溃、租约过期和租户不匹配的行为测试。
- AI 异步任务改为 MySQL 中的持久任务记录与 Outbox 事件在同一数据库事务内创建；Outbox Relay 使用有限批量、租约/原子状态转换和 RabbitMQ publisher confirms，失败可重试且不会无限快速重投。
- 消费者以任务 ID 幂等抢占任务；重复投递不得重复产生业务副作用。超过重试策略的任务进入可查询的失败状态，不返回伪成功。
- Redis 仅作为可重建的进度/状态缓存，不再是异步任务唯一真实来源；异步消息只传任务标识和最小可信上下文，不携带原始 Access Token、完整文档或敏感凭证。
- 数据库迁移只新增版本化迁移文件，不修改已应用迁移，不删除现存用户数据。

### 3.4 依赖故障隔离

- 为 Feign 和外部模型/Rerank 调用设置可配置连接与读取超时。
- 对幂等且可重试的查询使用有限重试；对写操作不做盲目重试。
- 为关键远程依赖增加熔断和并发隔离。AI 或 Rerank 不可用时，RAG 可按既定安全策略降级为本地/基础检索；文档权限检查失败必须拒绝访问，不能降级放行。
- 错误响应明确表示依赖不可用或任务排队，不伪造成功结果。

### 3.5 指标、告警与数据恢复

- 复用 Actuator/Micrometer/Prometheus，补充异步任务队列积压、任务成功/失败/重试、Outbox 待发布量、模型调用错误与延迟、限流拒绝等低基数指标。
- 提供 Prometheus 抓取配置和可导入告警规则，告警覆盖服务不可用、错误率/延迟超目标、Outbox 积压、任务积压及依赖故障。
- 备份脚本不得把数据库密码作为命令行参数暴露；备份文件校验和、权限与保留清理均有安全边界。
- 恢复演练只在明确命名的隔离数据库/临时卷进行，校验后自动清理临时资源；禁止对生产业务库执行 DROP/覆盖。
- 运维说明要求备份离机保存，并记录最近一次恢复验证的结果、耗时和可恢复时间点。

## 4. 非目标

- 本阶段不部署跨地域双活或承诺具体的商业 SLO 数字。
- 不把 Compose 的 `deploy.replicas` 当作跨主机高可用实现；多节点编排和有状态中间件集群在后续阶段处理。
- 不引入 XA/JTA、Seata 或全局强一致事务。异步跨服务流程使用数据库 Outbox、至少一次投递、幂等消费者和明确失败状态。
- 不更换现有 JWT、租户模型、API 路径或本地开发端口映射。
- 不将 Prometheus 指标标签设置为用户 ID、文档 ID、查询文本等高基数或敏感值。

## 5. 测试策略

所有行为改动按测试先行实施。测试使用真实业务类和隔离依赖；仅对外部模型或 RabbitMQ 传输边界使用精确的替身，数据库事务与迁移使用真实隔离数据库验证。

必须覆盖：

1. 未认证、伪造身份头、跨租户文档/任务/RAG 内容访问均被拒绝。
2. Redis 限流不可用时请求不会绕过限流或认证；合法用户限流与未认证来源限流边界正确。
3. AI 任务数据库提交成功但发布失败时 Outbox 可恢复；数据库事务回滚时任务和 Outbox 均不可见；重复事件只执行一次有效状态转换。
4. 消费者崩溃、租约到期、重复消费和毒消息均产生可预期任务状态，且不泄露敏感上下文。
5. 外部依赖超时/错误触发有界熔断与安全降级；权限服务失败时拒绝访问。
6. 指标名称和值不包含敏感文本或高基数标签；告警规则可被 Prometheus 解析。
7. 备份脚本不将密码写入命令行；恢复演练使用隔离资源，验证失败也能安全清理。
8. Compose 配置校验仍确保生产公网端口仅为 80/443，开发环境仍可本地启动。

完成前执行 Maven 全模块测试、前端测试与构建、生产 Compose 配置校验、Prometheus 配置校验，以及新增的隔离数据库/消息可靠性测试。无法在当前机器验证的跨主机切换必须单独列为待人工演练，不得声称已经通过。

## 6. 交付标准

- P0 每个安全或可靠性行为都有针对性回归测试，并完成失败用例验证。
- 全模块后端、前端和部署配置验证通过；任何未通过项明确列出。
- 生产数据和密钥未被读取、改写或输出；所有数据迁移可向前兼容并可审计。
- README/运维文档准确说明本地 Compose 与多节点生产部署的能力边界。
- 交付报告包含改动清单、测试命令与结果、剩余人工演练步骤和未覆盖风险。
