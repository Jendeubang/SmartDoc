# SmartDoc 安全与可靠性加固设计

## 1. 背景与目标

SmartDoc 当前已经具备面向面试展示的完整业务链路，但代码审查发现九项需要加固的问题，涉及文件查询、网关认证、跨域、Docker 网络、文件上传、异步任务和 RAG 权限检索。

本次改造面向“单机公网展示环境”，目标是在保留现有功能和技术栈的前提下，完成安全边界、数据一致性、任务恢复能力和检索隔离加固。项目不引入 Kubernetes、分布式事务协调器或独立认证中心。

## 2. 全局约束

- 所有改动按五个阶段依次实施，每个阶段独立测试、评审和提交。
- 不在 Redis、MySQL、RabbitMQ 消息或日志中保存用户原始 Access Token。
- 数据库结构只允许通过新增 Flyway 迁移修改，不编辑已经执行过的迁移。
- 所有外部输入使用白名单、范围限制或结构化解析，不直接拼接 SQL。
- 生产环境只向公网暴露 80/443；数据库、中间件和微服务端口只在容器网络内可见。
- 跨企业数据必须在候选生成前完成租户隔离，未授权内容不得发送给 Rerank 或大模型。
- 失败流程必须有明确状态和补偿动作，禁止捕获异常后继续返回成功。
- 保持现有 API 响应结构兼容；确需调整时由后端先兼容旧字段。
- 第一阶段完成前不实施后续阶段业务改造。

## 3. 五阶段范围

### 3.1 第一阶段：直接安全风险

第一阶段包含五项加固：

1. 文件元数据排序字段白名单与分页边界。
2. 工具箱异步任务移除原始 JWT 持久化。
3. 网关认证改为 Spring Security 默认拒绝模型。
4. CORS 改为环境配置驱动的精确来源白名单。
5. 生产 Docker 配置隐藏内部服务端口。

阶段验收要求：认证、登录、刷新令牌、公开分享、文件列表、工具箱任务和 WebSocket 基础链路保持可用；恶意排序参数、伪造身份头、错误内部令牌、恶意 Origin 和公网内部端口访问均被拒绝。

### 3.2 第二阶段：文件数据完整性

文件上传使用补偿事务：先验证与扫描，再上传临时对象，写入 `PENDING` 元数据，切换正式对象并更新为 `READY`。任一步失败都执行对应清理或失败状态更新。重复文件仅在新文件完整成功后替换旧文件，避免失败上传破坏现有文件。

### 3.3 第三阶段：工具箱任务可靠持久化

MySQL 作为工具箱任务状态的唯一真实来源，RabbitMQ 负责调度，Redis 仅作为缓存和进度通道，MinIO 保存结果文件。任务消费通过原子状态转换保证幂等，支持重启恢复、失败重试和结果过期清理。

实现约束：`toolbox_job` 记录用户、组织、源文档列表、状态、重试次数、结果对象键和过期时间；消费者只有在 `PENDING` 或租约过期的 `PROCESSING` 状态上才能原子抢占任务，完成后以 `PROCESSING -> SUCCESS/FAILED` 条件更新。结果正文使用组织、用户和任务 ID 组成的 MinIO 对象键，Redis 不保存结果二进制。文档服务启动定时恢复器，限批量重新投递旧 `PENDING` 任务、回收停滞处理任务，并先删除过期 MinIO 对象再将任务标记为 `EXPIRED`；删除失败时保留原任务状态以便下次重试。

### 3.4 第四阶段：流式文件处理

普通上传改用可重复输入流写入临时对象，分片合并使用服务端临时文件按序流式拼接后再上传，避免把完整文件和所有分片加载进 JVM 堆。批量上传增加单文件、文件数和总容量上限，并在首次写入前完成预检；当前批处理按顺序执行，天然将单批并发限制为 1。

### 3.5 第五阶段：权限感知 RAG 候选生成

HNSW 索引按 `organizationId + knowledgeBaseId` 隔离，并在向量元数据中保留模型与维度信息。检索前获取授权文档集合，HNSW、Redis 向量检索和 BM25 同时应用该集合；只有授权候选才进入混合融合、Rerank 和 Prompt 构建。空授权集合直接返回空结果，不扩大为全库检索。

## 4. 第一阶段详细设计

### 4.1 排序字段与分页边界

`FileMetadataController` 继续接收原有 `sortBy`、`sortDirection`、`page` 和 `size` 参数，服务层通过固定映射把外部字段转换为数据库列名：

| API 字段 | 数据库列 |
| --- | --- |
| `createTime` | `create_time` |
| `updateTime` | `update_time` |
| `fileName` | `file_name` |
| `fileSize` | `file_size` |

未知排序字段不进入 SQL，统一回退到 `create_time`。排序方向仅接受不区分大小写的 `asc` 和 `desc`，其他值回退为降序。`page` 限制为最小 1，`size` 限制为 1 至 100。

测试覆盖合法字段、非法字段、SQL 片段、非法方向、负数页码和超大分页。

### 4.2 异步任务身份上下文

工具箱任务只持久化不可变身份上下文：

```text
jobId
userId
organizationId
operationType
documentIds
createdAt
expiresAt
```

任务创建接口仍使用用户 Access Token 完成入口认证，但任务入队前删除原始 `Authorization`。消费者调用内部文件接口时携带服务端生成的内部服务令牌，以及经过校验的用户、企业和任务上下文。

文件服务只有在内部服务令牌有效时才信任内部用户上下文头。普通客户端提交的 `X-User-Id`、`X-Role`、`X-Organization-Id` 和内部令牌头必须由网关清除。

任务执行不依赖用户 Access Token 的剩余有效期；用户退出后，已授权并进入队列的任务可以继续，但管理员强制停用用户后，新任务必须被拒绝。第一阶段不改变任务状态存储架构，完整持久化在第三阶段完成。

### 4.3 网关默认拒绝认证

认证职责调整为：

1. 前置 WebFilter 删除所有客户端可伪造身份头。
2. Spring Security 的认证过滤器解析 Bearer Token，校验签名、类型、有效期、会话和撤销状态。
3. 成功认证后把用户、角色、企业和会话信息写入 `SecurityContext`。
4. 授权规则只放行明确公开路径，其余路径要求已认证。
5. 网关全局过滤器负责可信请求头注入、Trace ID、日志和限流，不再维护第二份认证白名单。

公开路径包括登录、注册、刷新令牌、忘记/重置密码、公开分享内容和 Actuator 健康检查。刷新令牌只能访问刷新接口。由于浏览器 SockJS 传输握手无法稳定携带 Bearer Header，`/ws/**` HTTP 传输端点保持公开，但 AI 与文档服务必须在 STOMP CONNECT 阶段验证 Access Token，并在 SUBSCRIBE 阶段校验用户与资源归属。

为降低切换风险，新认证链路先由自动化测试覆盖旧白名单，再替换旧的 `AuthGlobalFilter` 认证分支；不得同时保留两套独立认证判断。

### 4.4 CORS 精确来源

共享 Web MVC 与网关 WebFlux 均读取同一语义的配置：

```text
SECURITY_CORS_ALLOWED_ORIGINS
```

该配置使用逗号分隔的精确 Origin。开发默认值为 `http://localhost:5173`，生产环境必须显式配置 HTTPS 域名。配置为空时生产环境启动失败，非生产环境回退本地开发地址。

系统使用 Bearer Token 而非跨站 Cookie，因此默认 `allowCredentials=false`。只允许实际使用的 HTTP 方法和请求头。预检请求由网关统一处理，后端服务保留同样白名单作为绕过网关时的防御层。

### 4.5 Docker 生产网络边界

开发和生产 Compose 明确分工：

- `docker-compose.yml`：公共服务定义和内部网络。
- `docker-compose.dev.yml`：本地调试端口映射。
- `docker-compose.prod.yml`：生产资源限制、只读配置和 Nginx 入口。

生产环境宿主机只发布 80/443。网关、用户服务、文件服务、AI 服务、文档服务、MySQL、Redis、RabbitMQ、MinIO 和 Nacos 只使用 `expose` 或容器网络，不声明宿主机端口映射。

增加只读检查脚本解析 `docker compose ... config` 输出；若生产合成配置发布除 80/443 之外的端口，检查失败。README 的生产启动命令必须明确带上生产 Compose 文件，避免误用开发配置。

## 5. 错误处理与兼容性

- 参数校验失败返回 400；认证失败返回 401；权限不足返回 403；限流返回 429。
- 内部服务认证失败不能转换为通用 500。
- CORS 拒绝不暴露内部错误详情。
- 第一阶段不修改前端已有接口路径和成功响应结构。
- 环境变量新增项提供 `.env.example`，真实密钥和域名不提交仓库。
- 开发环境保留本地端口调试能力，生产环境配置不复用开发端口映射。

## 6. 测试策略

第一阶段必须新增以下回归测试：

- 文件排序字段白名单、方向和分页边界测试。
- Redis/任务消息中不存在 Bearer Token 的测试。
- 内部服务令牌正确、错误、缺失和伪造用户上下文测试。
- 网关公开路径、受保护路径、Access Token、Refresh Token、过期、撤销和伪造头测试。
- MVC 与 WebFlux CORS 的允许来源和拒绝来源测试。
- 生产 Compose 端口暴露检查。

每项先编写失败测试，再实现最小改动。阶段完成时执行：

```powershell
mvn test
npm test
npm run build
```

并运行第一阶段安全回归测试及生产 Compose 配置检查。

## 7. 提交与回滚

第一阶段拆分为五个独立业务提交，测试或文档调整可跟随对应提交：

```text
fix: whitelist file metadata sort fields
security: remove bearer tokens from toolbox jobs
security: enforce gateway authentication by default
security: restrict cors origins
ops: isolate production service ports
```

网关认证切换是第一阶段风险最高的改动，必须在单独提交中完成。任何回归只回滚当前提交，不回滚已经验证通过的前序加固。第一阶段不执行破坏性数据库变更。

## 8. 完成定义

第一阶段只有同时满足以下条件才算完成：

- 五项加固全部实现并具有针对性自动化测试。
- 后端全量测试、前端测试和生产构建通过。
- 登录、刷新、退出、文件列表、文件下载、工具箱任务、公开分享和 WebSocket 冒烟验证通过。
- Git 工作区只包含预期修改，不包含密钥、构建产物和本地配置。
- 生产 Compose 仅发布 80/443。
- 本阶段修改经过一次独立代码审查，未发现阻断级问题。
